# Infrastructure Demarcation Strategy v1.0

## 1. The Core Identity of ZQK
ZQK (Zen Quantum Kernel) is fundamentally a **CLI-first desktop operating system and knowledge kernel** designed to maximize the capabilities of human and AI collaboration on a local host machine. It is *not* a distributed cloud microservices platform.

The architectural conflict identified during the "Specialized Subkernels & Brand Assets Strategy" session exposed a critical risk: allowing cloud-native paradigms (e.g., KEDA autoscaling, massive federated graph partitions, distributed tracing across sub-kernels) to bleed into the core ZQK CLI architecture will inevitably crush the local host machine under extreme IPC and OS process overhead.

## 2. Demarcation Boundaries

To realize the "universe-denting" capabilities of a ZQK swarm without bloating the core CLI, we must strictly demarcate the boundaries between **Local Kernel Operations** and **Serverless Ecosystem Utilities**.

### A. The Local ZQK Kernel (The Control Plane)
- **Role:** Orchestration, state management, traceability, and semantic context aggregation.
- **Form Factor:** Lightweight compiled Go binary (`zqk`).
- **Data Layer:** Single-instance graph database (Neo4j/MemGraph) optimized for metadata, taxonomy, and object relationship mapping.
- **Execution:** Fast, synchronous (or structured concurrency via internal Goroutine Manager) CLI executions. Avoids massive remote procedure calls.

### B. Cloud-Based Utility Subkernels (The Compute Plane)
- **Role:** Heavy computational tasks, advanced multi-modal generative tasks (e.g., Audio/Video rendering, massive parallel compilation, deep embedding generation).
- **Form Factor:** Serverless cloud functions, decoupled MCP (Model Context Protocol) external servers, or managed Kubernetes clusters (external to the ZQK binary).
- **Data Layer:** Scalable edge-cached object storage (S3, Cloudflare R2) for large binary blobs (images, audio).
- **Integration:** The Local ZQK Kernel delegates tasks to these serverless utilities via standardized APIs (e.g., HTTP webhooks, lightweight external MCP calls). The cloud utilities execute the intensive work and respond with a finalized artifact or signed URI, which ZQK then registers into its lightweight graph DB as a traceable object.

## 3. The Path Forward

1. **No Distributed Monoliths:** We will reject any architecture that requires ZQK to natively manage a federated, distributed graph across multiple nodes. 
2. **MCP as the Boundary:** The Model Context Protocol will act as the strict boundary between the lightweight ZQK orchestrator and any heavy "Specialized Subkernels." If an agent needs specialized A/V tools, ZQK connects to an external, serverless MCP server that possesses those tools, rather than attempting to natively host the computation.
3. **Blob Offloading:** Large creative or data assets generated by agents will *never* be encoded into the ZQK graph. They will be stored in designated file directories or cloud buckets, with only their metadata and pointers tracked in ZQK objects.

By strictly enforcing this demarcation, ZQK remains blistering fast and localized for humans and their AI swarms, while gracefully leveraging the infinite compute of the broader cloud ecosystem when required.
