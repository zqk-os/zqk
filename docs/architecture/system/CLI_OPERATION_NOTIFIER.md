## CLI Operation Notifier Pattern

**Last Verified:** 2026-08-31


### Purpose

Provide a **standard, reusable pattern** for surfacing long‑running CLI operations (like `system check`) to humans and agents:

- Single **operation spine** via the coordination system (`pkg/coordination`).
- Shared **operation ID** and **operationType** across phases (discovery, validation, auto‑fix, etc.).
- Pluggable **notifiers** (terminal, MCP clients, dashboards) that subscribe to the same events.

### Core Concepts

- **OperationType**: Logical name for the operation, e.g. `system_check`, `scheduler_job`, `migration`.
- **OperationID**: Unique identifier for a specific run, generated by the CLI entrypoint (e.g. `check_123456789`).
- **Coordinator Events**:
  - Emitted via `coordination.EventCoordinator`.
  - Carry a small, well‑defined metadata schema per `operationType`.
  - Routed to:
    - Logging (structured logs).
    - Audit (persistent `audit_event` objects).
    - Metrics (metric pipeline).
    - Operational (subscribers such as CLI notifiers, MCP emitters, schedulers).

### System Check Implementation

**Files**:

- `cmd/zqk/system/async_check.go`
- `cmd/zqk/system/async_check_helpers.go`
- `cmd/zqk/system/check_follower.go`
- `cmd/zqk/system/check_progress_coordination.go`
- `cmd/zqk/system/discovery_coordination.go`

**Operation identity**:

- `runCheckAsyncNonBlocking` and `runCheckAsyncWithFollow` generate an `operationID` of the form `check_<timestamp>`.
- This `operationID` is threaded into:
  - `CoordinatorOperationCallback` (start / complete / error).
  - Discovery helpers (`emitDiscoveryStartEventViaCoordinator`, `emitDiscoveryProgressEventViaCoordinator`).
  - Validation progress (`emitCheckProgressEventViaCoordinator`).

**Event schema (system_check)**:

Common fields in `EventData.EventData.MetricsData` and `LoggingFields`:

- `phase`: `"discovery"`, `"validation"`, `"auto_fix"`, `"finalizing"` (today we use `discovery` and validation).
- `progress`: number of units completed (for validation: validated objects).
- `total_tasks`: total work units in this run.
- `files_found`: discovery‑phase count (overall or per‑kind).
- `queue_size`: current validator queue size.
- `elapsed_seconds`: time since phase start or overall start.
- Optional `hint` / `progress_message` for UX guidance.

All of these are emitted with:

- `operationType = "system_check"`.
- `operationID = <same ID>` from the CLI entrypoint.

### Terminal Notifier (CLI)

**File**: `cmd/zqk/system/check_follower.go`

- Implements `TerminalProgressSubscriber`, a `coordination.OperationalEventSubscriber` that:
  - Subscribes to `operation.progress`, `operation.start`, `operation.complete`, `operation.error`.
  - Filters on:
    - `event.OperationType == "system_check"`.
    - Matching `operationID`.
  - Renders:
    - **Discovery phase** (`phase = "discovery"`):
      - `Discovering [<kind> ]objects... <files_found> found (<elapsed_seconds>s)`.
    - **Validation phase** (default when `phase` is not `"discovery"`):
      - `System check progress: <percent>% (<progress>/<total_tasks>, queue: <queue_size>)`.
  - Deactivates itself on `operation.complete` / `operation.error`.

The notifier is wired in `runCheckAsyncWithFollow`, which:

- Generates `operationID`.
- Starts the async check with `runCheckAsyncWithContextAndOperationID`.
- Subscribes:
  - `CheckCompletionSubscriber` (completion/error).
  - `TerminalProgressSubscriber` (progress heartbeat).

### Coordinator Emission Strategy

For **system_check** we emit via two coordinators:

1. **Storage‑backed coordinator** (per‑call):
   - Uses `StorageAuditRouter` and default logging router.
   - Responsible for **persistent audit logs and structured logging**.
2. **Global coordinator**:
   - `coordination.GetCoordinator()` with default routers.
   - Responsible for **in‑process operational subscribers** such as:
     - `TerminalProgressSubscriber` (CLI).
     - MCP event emitters.
     - Other agent/daemon subscribers.

Discovery and validation helpers emit to **both**:

- Storage‑backed coordinator: full channels (logging/audit, metrics where appropriate, operational).
- Global coordinator: **operational‑only** events, reusing the same `operationID`, `operationType`, and metadata.

### How to Reuse for Other Commands

To adopt this pattern for another long‑running command (e.g. `scheduler` operations):

1. **Define the operation type and schema**
   - Choose an `operationType` string (e.g. `"scheduler_job"`).
   - Document the event metadata fields for that type (phase, progress, queue, etc.).
2. **Generate and thread an `operationID`**
   - In the CLI entrypoint:
     - Generate `operationID` and pass it into the core implementation.
3. **Emit events through coordination**
   - Use helpers similar to `emitCheckProgressEventViaCoordinator` / `emitDiscovery*ViaCoordinator`:
     - Emit via storage‑backed coordinator for audit/log/metrics.
     - Emit via global coordinator (operational‑only) so subscribers can react.
4. **Attach a notifier**
   - Implement a small notifier type (modeled on `TerminalProgressSubscriber`) that:
     - Implements `coordination.OperationalEventSubscriber`.
     - Renders a concise heartbeat line plus key state transitions to stderr.
   - Subscribe/unsubscribe it in the command’s `--follow` (or equivalent) path using:
     - `coordination.GetCoordinator().Subscribe(...)`.

This ensures:

- **Agents and humans see the same operation story** (same `operationID` and metadata).
- **CLI UX is consistent**: every long‑running command can have a heartbeat notifier without ad‑hoc printing.
- **Multi‑agent / multi‑process setups** can coordinate via a shared event stream backed by storage.
